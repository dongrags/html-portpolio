Case study · Invoiceror

Field notes: three production bugs and how I fixed them

Dalmacio 'Dhong' Ragudo · September 2026

Most of Invoiceror's code is written by AI coding agents that I direct. My job is the part around them: reading what they produce, finding what is wrong when production misbehaves, fixing the root cause and verifying the result. These are three real incidents from that work.

The system

Invoiceror is a production invoicing and business management platform: a React + TypeScript web app, the same codebase shipped to Android with Capacitor, and a Supabase backend — PostgreSQL with 300+ migrations, row-level security policies, SQL functions and pg_cron scheduled jobs, plus Edge Functions for email delivery, the AI assistant and Stripe webhooks.

The source code is private because Invoiceror is a commercial product. The excerpts below are trimmed to the relevant lines, with customer data removed.

Incident 1 · Broke in production

Reminder emails arrived with the wrong time

Symptom

A user in Kuala Lumpur scheduled an activity for 10:00 PM. The reminder email said 06:00 AM GMT+8 — eight hours off, and on the next day.

Root cause

Activity times are stored as the user's local date and time with no timezone attached (date: "2025-12-12", start_time: "22:00"). The notification Edge Function built a Date from those strings, which the server interprets as UTC, and then converted it to the user's timezone — so a time that was already local got shifted a second time.

// Before: "2025-12-12T22:00" is parsed as 22:00 UTC on the server…
const appointmentDateTime = new Date(`${appointment.date}T${appointment.start_time}`);
const formattedTime = appointmentDateTime.toLocaleString('en-US', {
  hour: '2-digit', minute: '2-digit', timeZone: userTimezone, timeZoneName: 'short'
});  // …then shifted +8h again → 06:00 AM

Fix

Treat the stored value as what it is — the user's local wall-clock time — and format it without any conversion, then append the user's timezone label.

const [hours, minutes] = appointment.start_time.split(':').map(Number);
const time12hr = new Date(2000, 0, 1, hours, minutes)
  .toLocaleString('en-US', { hour: '2-digit', minute: '2-digit', hour12: true });
// 22:00 → "10:00 PM", then + " MYT (GMT+8)"

Verification

Tested an evening (10:00 PM) and a morning (7:00 AM) activity in the Kuala Lumpur timezone and confirmed both reminder emails showed the time the user had set, then deployed the updated function.

What I would tighten next: the timezone label for Malaysia is currently special-cased. The durable fix is to store activities as timestamptz with the user's zone, so every consumer — email, push, calendar — reads the same unambiguous instant.

Incident 2 · Found by reading a query

The AI assistant could create customers it had no permission to create

Symptom

When a user asked the AI assistant to "create an invoice for" a business that was not in their customer list, a new customer record appeared that nobody had added — with only a name, no email, phone or address.

Root cause

The AI's invoice tool is backed by a PostgreSQL function. Reading it, the lookup-by-name had a fallback: if no customer matched, the function inserted one. That meant a typo or a hallucinated name from the model silently wrote to the clients table — the tool's scope was "create invoices", but the function could also create customers.

SELECT id INTO v_client_id
FROM clients
WHERE user_id = p_user_id
  AND LOWER(TRIM(name)) = LOWER(TRIM(p_customer_data->>'name'));

IF v_client_id IS NULL THEN
  INSERT INTO clients (user_id, name, company, email, phone, address)
  VALUES (p_user_id, TRIM(p_customer_data->>'name'), '', '', '', '')
  RETURNING id INTO v_client_id;
END IF;

Fix

A new migration replaced the fallback with an explicit, machine-readable error, so the assistant tells the user the customer was not found and asks them to add it — customer creation stays a deliberate user action.

IF v_client_id IS NULL THEN
  RETURN jsonb_build_object(
    'success', false,
    'error_code', 'CUSTOMER_NOT_FOUND',
    'error', format('Customer "%s" not found. Please add this customer first.', v_customer_name)
  );
END IF;

Why it matters: an AI tool should never be able to do more than the permission it was given. When I review agent-built features I now check the database functions behind each tool, not only the prompt and the UI.

Incident 3 · Found by reading agent-written code

The voice assistant hung forever on "Processing…"

Symptom

After speaking a command to the AI voice assistant, the UI showed "Processing…" indefinitely. The console showed "Auto-sending message" and then nothing — no request ever reached the AI endpoint.

What did not work first

An earlier change added a 45-second timeout. It never fired, because the problem was not a slow request — the request never started. Treating the symptom hid the real bug for another release.

Root cause

Reading the code path end to end: the speech handler set isLoading = true and then called sendMessage(). But sendMessage() begins with a guard that returns early whenever isLoading is already true. So the caller switched the loading state on, and that exact state made the function it called do nothing.

// Speech handler (caller)
setIsLoading(true);
await sendMessage();

// sendMessage()
if (!inputMessage.trim() || !currentConversation || isLoading) return;  // ← always returned

Fix

Let sendMessage() own its loading state: remove the caller's setIsLoading(true), and wait for the pending input-state update before sending. Tested by speaking a command and checking the console for the outgoing request and the AI response.

What I would tighten next: the short wait for React state is a workaround. Passing the recognised text into sendMessage(text) as an argument removes the dependency on state timing altogether.

How I work on incidents

  • Reproduce first — get the failing case and the logs before changing anything.
  • Read the real code path — including SQL functions and Edge Functions, not just the component that shows the error.
  • Fix the root cause, and be suspicious of fixes (like a timeout) that make a symptom disappear.
  • Verify on production with the same case that failed.
  • Write it down — Invoiceror's fixes are documented in short written notes (over 100 so far): symptom, cause, change, verification. This page is three of them.
